## Mission

Two ways to run the same tool — a portable, click-and-use **desktop app** and a
**self-hosted web app** (browser UI over the same engine and command layer) —
for **animated (moving) images only**: **GIF, APNG, and WebP**. It should let a
*normal person* edit, optimize, and convert animated images without ever seeing
"a pile of code scrap."

**Scope honesty (external review J:F-17, dispositioned S24):** today the product
is GIF-only — APNG/WebP are 0% built and formally deferred to 2.0.0+ (see the
format plan below and `STATUS.md` D-01..D-03). The README title carries
"work-in-progress" and both the README roadmap and this file state the
deferral, so the pitch is a mission statement, not a ship promise.

**2026-09-12 (S14) — direction amendment (owner):** the `web/` build is a
**supported product surface** — an alternative to the `.exe`/portable build for
users who prefer a browser UI. It is **self-hosted**: same engine, same command
semantics, loopback by default with `GS_WEB_HOST` opting into a LAN bind. The
offline-only promise ("no cloud, no telemetry") is unchanged — a hosted/cloud
deployment would be a separate decision needing its own privacy decision.
Desktop stays the 1.0.0 release artifact. Split rules + plan template:
`web/WEB_PLAN_TEMPLATE.md` (state line mirrored in `SESSION_HANDOFF.md`, gate
**G16**).

**Adopted amendment 2026-10-08 (owner, `OD-20 = a` — S38; proposed S24 and
registered as `U-90`/`P3-19`):** the C# plan's scope list
(`docs/planning/PLANNING.md` §2) carried an owner request (2026-09-14) for
still-image collections → animated, and video strictly as conversion endpoints.
The owner has now adopted it, so **"Not photos, not video" is narrowed to
"photos and video only as CONVERSION ENDPOINTS / inputs — never as the
subject."** The words changed first, which was the gate; code may now follow the
boundaries below.

**The adopted boundary (`OD-20 = a`, in force):**
1. **One** FFmpeg sidecar, scoped strictly as a conversion endpoint. It
   **decodes in** (video → frames, stills → frames); **gifsicle still does all
   the GIF work** and remains the only encoder for GIF outputs. No editing,
   timeline, capture or playback UI — this is a converter, not an editor, and
   ScreenToGif's recorder/editor scope is explicitly OUT.
2. **Subprocess only.** The sidecar is a separate executable invoked over argv,
   exactly like gifsicle — never linked into the Ms-PL UI, never vendored
   in-process. (The in-process carve-out in this file belongs to the
   experimental `web/wasm/` track alone and does not extend here.)
3. **Its own licence note ships with it.** FFmpeg builds are LGPL **or** GPL
   depending on configuration, so the build's licence must be identified, its
   text staged beside the binary, and its notices carried in the package —
   per `docs/legal/README.md` §5. The engine stays GPLv2-only and the first-party
   UI stays Ms-PL; the sidecar adds a third, separately-licensed piece.
4. **Not on the 1.0.0 critical path.** The shipped 1.0.0 artifact is still the
   Windows GIF tool (`OD-17 = a`); this is additive scope with its own rows.

**Still gated after the amendment:** `U-90` stays OPEN until the deferred rows
this scope needs actually exist (P3-19) — the amendment removes the
vision blocker, not the register one.

## Audience

Casual / non-technical users who just want it to work, **plus** power users who
want the full gifsicle terminal control underneath.

## UX references

- **"Feels & vibe" of XNConvert** for the overall layout and ease of use.
- **Feature-richness of eZgif** for GIF-style options + a "Convert / other"
  branch (convert between formats, explode, merge, reorder frames, and so on).

## UI approach (owner decision — licence story lives in `docs/legal/README.md`)

- **No Caesium base** (dropped S18, `OD-09 = b`): the look-and-feel is rebuilt
  from open parts — system fonts and MIT/Apache-licensed icon sets — with no
  third-party files. Rationale: `docs/legal/README.md` §1.
- Model the layout/feel on **XNConvert** for ease of use. Workflow imitation
  uses no third-party files; no branding copied.
- **Desktop UI direction (S19/OD-C7, resumed S38):** the shipped exe stays
  **C++17/Qt6 through 1.0.0**; the C#/WPF shell is **RESUMED** (`OD-C7 = resume`,
  owner 2026-10-08) as an additive lane behind the CLI oracle — Phase 2
  (`Gifscythe.Core` + the CLI-parity gate) is in progress and CI-proven, the WPF
  shell is not started (resume point / plan: `docs/planning/PLANNING.md` §2). The
  1.0.0 artifact still finishes on C++17/Qt6; the C# lane must not displace it.

## Hard scope constraints

- **Exclusively** animated GIF, APNG, and WebP — the *subject* is the moving
  picture. Photos and video are **inputs to a conversion endpoint only**, never
  the subject (adopted 2026-10-08, `OD-20 = a`: one FFmpeg sidecar, decode-only,
  subprocess, its own licence note — see the amendment above).
- Portable, click-and-run (no installer, no admin). Windows-first (S20/OD-17:
  the shipped product is the Windows exe + the web app; Linux is the CI/sandbox
  test battery and ships nothing).
- **Offline-only** (2026-09-09): no server, no auto-update, no telemetry. The
  web surface is self-hosted, which keeps this promise.
- Retain gifsicle terminal-level control for power users (live command pane,
  honest **one-way** through 1.0.0 per `OD-12 = a`; argv execution — never
  shell injection).
- gifsicle stays a **subprocess** (GPL v2-only engine vs Ms-PL UI). The one
  carve-out is the experimental `web/wasm/` in-process track, which is exactly
  why `OD-16` blocks it from shipping (`docs/legal/README.md` §3–§4).
- **Never call it 1.0.0** until the UI/UX task is done and the release criteria
  in `docs/release/RELEASE_PROCEDURE.md` are met (0.2.0 may come first per the
  minor-bump rule; version stays 0.1.0 per `OD-11 = a`).

## Architecture (of record — from the 2026-09-06 feasibility review)

**Verdict then, unchanged since:** this is a new desktop app *around* gifsicle,
not a tweak inside it. Two things were genuinely hard — licence mixing (solved
by the subprocess boundary + the S18 Ms-PL relicence) and WebP/APNG codecs
(gifsicle reads/writes GIF only; `grep webp|apng|png` over its source: zero
hits — hence the deferred multi-format phase with its own codec subprocesses).

```
  +---------------------------------------------------------------+
  |  UI surfaces: Qt6 Widgets desktop (shipped) · web browser UI   |
  |   (self-hosted, supported) · C#/WPF shell (PARKED)             |
  |   file queue · per-file settings · before/after preview ·      |
  |   live one-way command pane (shows exactly what runs)          |
  +-------------------------------+-------------------------------+
                                  | builds a gifsicle argv (array, never a shell)
                                  v
  +---------------------------------------------------------------+
  |  CONTROL LAYER  src/core/*.h — header-only C++17, Qt-free:     |
  |   Settings · command builder · Validate · OutputPlan/Name ·    |
  |   ProcessRunner · OutputVerify/ExplodeVerify · EngineLocator   |
  |   Mirrors: web/command.mjs + web/validate.mjs (parity-pinned)  |
  +-------------------------------+-------------------------------+
                                  v
  |  ENGINE: gifsicle 1.96 (GPL v2-only) as a SEPARATE SUBPROCESS  |
  |  Future multi-format: libwebp / libpng+APNG helper processes   |
  +---------------------------------------------------------------+
```

- **MVP wiring (shipped):** subprocess wrapper — cleanest for licensing, zero
  engine refactor, portable. The later "in-process libgifsicle" idea is exactly
  what the wasm track explores, and it changes the licence math (OD-16).
- **Preview vs truth:** Qt `QImage`/`QMovie` is fine for UI preview, but real
  animated encode/decode semantics (delay/disposal/transparency) belong to the
  codec layer — never infer engine behavior from QImage.
- **Engine truth over tables:** where this file's mapping and the engine
  disagree, the engine wins (the audit's VP-1..VP-5 guardrails in
  `COMPILED_AUDIT.md` §15.1 exist because of exactly that class of drift).

### GUI control → gifsicle argument mapping (the product's core table)

Corrected in S24 per guardrail VP-5: crop uses the engine's plus form.

| GUI control | gifsicle argument |
|---|---|
| Optimization level slider | `--optimize=0..3` (0 = off — VP-2) |
| Lossiness slider | `--lossy=0..200` |
| Colors dropdown/slider | `--colors=N` (2–256) |
| Dither dropdown | `--dither=floyd-steinberg|ro64|none` (parameterised grammar — deliberately not enum-validated) |
| Resize (fit/exact/touch/width/height) | `--resize WxH`, `--resize-fit`, `--resize-touch`, `--resize-width`, `--resize-height` |
| Scale % (X/Y) | `--scale XxY` |
| Rotate | `--rotate-90/-180/-270` |
| Flip | `--flip-horizontal`, `--flip-vertical` |
| Crop box | `--crop X,Y+WxH` (**plus form — VP-5: the code is right**), `--crop-transparency` |
| Loop count | `--loopcount=0` forever (VP-1) · `N` times · `--no-loopcount` play once · unset = engine default |
| Per-frame delay (1/100 s, **not** ms) | `-d` |
| Disposal dropdown | `--disposal=N` (0..7) |
| Transparency color picker | `--transparent=#RRGGBB`, `--no-transparent` |
| Background color | `--background=#RRGGBB` |
| Logical screen | `--logical-screen WxH` |
| Colormap transform | `--change-color`, `--color-transform`, `--use-colormap`, `--colormap-algorithm` |
| Comments | `--comment="..."`, `--no-comments` |
| Gamma / color math | `--gamma=srgb` / `--gamma=oklab` / `--gamma=NUM` (string form; `-1` sentinel = unchanged — VP-3) |
| Threads | tri-state: unset = no flag (engine default, 1 thread) · `0` = bare `-j` (auto, 8) · `N>0` = `-jN` (DS-06) |
| Frame ops | `#0 insert-1 #2 ...`, `--delete`, `--replace`, `--append` |
| Mode | batch (`-b`), merge (`-m`), explode (`-e`, verified frames only) |
| Robustness | `--careful`, `--conserve-memory`, `--no-warnings`, `--ignore-errors` |

That list *is* the product. High-value "smart" defaults (e.g. Auto-optimize =
`-O3 --lossy=20` + savings report) stay in scope; the settings surface the
layer does NOT model is documented per U-75 (web/README + CLI --help).
