## 1. The pick

> ### ✅ **U-01 — batch auto-naming silently destroys user data** (with **U-03** in the same pass)
>
> Fix-order **step 1** in the consolidated audit. The only Critical in the register
> that loses a user's file. All three independent audits raised it. And — the reason
> it is pickable rather than merely important — **the whole decision can be moved out
> of Qt into a Qt-independent core header**, so the part that decides whether a run
> is safe gets compiled and unit-tested here with plain g++, and the Qt change is a
> thin call site.

### 1.1 Reproduced, not assumed

**Case A — the output *is* the source.** Template `{name}.gif`, empty batch folder →
`defaultOutputFor()` (`MainWindow.cpp:527-531`) resolves `dir` to the input's own
folder, so target == input.

```
$ gifsicle self.gif -o self.gif          ; rc=0
   before  8703 B  md5 5ccf9df782db1fc3c59abebe01163d5f
   after   8703 B  md5 5e2d1d879d36bbe488dec14cdbcdc226      ← source replaced in place
$ gifsicle -O2 self2.gif -o self2.gif    ; rc=0
   before  8703 B → after 8671 B  md5 f75869cc3e155e5e0b9c6a792657780a
```

**Case B — two different inputs, one output.** `/d1/hero.gif` and `/d2/hero.gif`
queued, batch folder `/out`, default template → both render `/out/hero_opt.gif`:

```
d1/hero.gif  8703 B  5ccf9df7        gifsicle d1/hero.gif -o out/hero_opt.gif → rc=0
d2/hero.gif  6514 B  220dd69a        gifsicle d2/hero.gif -o out/hero_opt.gif → rc=0
out/hero_opt.gif  4476 B  af1d2b9d   ← d1's result is gone; both runs exited 0
```

The GUI's `onProcessFinished()` then reports `Optimization complete — 2 file(s).`

### 1.2 Why the existing guard does not catch it

`runCommand()` has exactly one collision check, `MainWindow.cpp:730`:

```cpp
if (inputs_.size() > 1 && templateIsConstant()) { … refuse … }
```

It fires only when the template has **no `{name}` at all**. Any template *with*
`{name}` is assumed safe — but `{name}` is `fi.completeBaseName()`, which is not
unique across a queue. Targets are then computed **one at a time, after the previous
process already finished** — `:756` for file 1 and `:872` for every later file — and
are never collected into a set, never compared to each other, never compared to the
inputs, never checked for pre-existence.

Harness **T16 does not cover it**: it uses `a.gif`/`b.gif` (distinct stems) inside one
`QTemporaryDir` and exercises only the constant-template refusal. The two paths above
are untested.

### 1.3 U-03 rides along because it is the same kind of lie

The GUI spinner shows **"Auto"** at 0 (`SettingsPanel.cpp:349 setSpecialValueText("Auto")`).
`GifsicleCommand.h:210` emits a flag only for `threads > 0`:

```
threads = -1 (default) → []      ← no -j at all
threads =  0 ("Auto")  → []      ← no -j at all
threads =  4           → [-j4]
```

and the engine's default is single-threaded:

```
reference_code/gifsicle/src/gifsicle.c:38   const int GIFSICLE_DEFAULT_THREAD_COUNT = 8;
reference_code/gifsicle/src/gifsicle.c:39   int thread_count = 0;
reference_code/gifsicle/src/gifsicle.c:1893   else thread_count = GIFSICLE_DEFAULT_THREAD_COUNT;  // bare -j
reference_code/gifsicle/src/xform.c:1329    int nthreads = thread_count;   // 0 → nthreads>1 false → 1 thread
```

`GifsicleSettings.h:75` even documents `-j; <=0 = auto`, which the builder never
implements. **Scope note the earlier audits omit:** `thread_count` is consumed only by
`resize_stream()`, so the blast radius is resize runs — real, but not whole-app.

### 1.4 Shape of the fix (and why it is verifiable here)

New Qt-independent header `src/core/OutputPlan.h`:

```
plan_outputs(inputs, batch_dir, template_render, explicit_out)
   → { ok, targets[], reason, offending[] }
     · rejects target == source for any pair
     · rejects two inputs mapping to one target
     · rejects target already on disk (overwrite policy, not silence)
```

* `MainWindow.cpp:730` / `:756` / `:872` collapse into **one** preflight that plans the
  whole batch before the first process starts; the batch loop consumes the plan
  instead of re-deriving each path.
* `GifsicleCommand.h:210` becomes `threads > 0 → "-jN"`, otherwise bare `-j`.
* **Verified here:** unit tests in `tests/test_gifsicle_command.cpp` (g++ only) cover
  every rejection path, plus a CLI-level end-to-end that proves a real batch run
  refuses instead of destroying.
* **Verified by CI only:** the Qt call site + a new harness case **T17** (same-shape
  files in two dirs; template `{name}.gif` with an empty batch dir). This is the one
  part I cannot compile in this sandbox and I am saying so up front.

## 4. One correction to the register

**U-19 does not hold as written.** The row says a real
`save_settings → load_settings` round trip returns `crop_w`/`crop_h` and `position`
as **0**. Run today against `src/core/SettingsIO.h` with the parent toggles **on**:

```
saved:  crop=true crop_x=3 crop_y=4 crop_w=200 crop_h=150
        position_x=12 position_y=7  resize_kind=scale scale_x=0.5 scale_y=0.5
reload: crop_w 200 → 200   crop_h 150 → 150
        position 12,7 → 12,7  (has_position 1 → 1)
        scale 0.5,0.5 → 0.5,0.5    load warnings: 0
```

Nothing is lost. The original `POST_S7_AUDIT.md` F-02 repro started from
`crop=false, has_position=false` — in which case *not* serialising the children is the
correct behaviour, because those fields are inert anyway. What survives is only the
**wording** problem: `SESSION_HANDOFF.md` calls `readFrom()` the "exact inverse" of
`writeInto()` without stating the toggle carve-out. That is a one-line doc edit, not a
Medium data bug. **Recommend U-19 be downgraded to a nit and re-worded.**

Everything else I re-tested held up, and two rows are *stronger* than written:
U-01 case A destroys the source even at the default no-flag setting (the earlier repro
needed an optimise flag to make it obvious), and U-02's folder also defeats
`verify_audit.sh`'s own D1/D2 completeness check.
